# 地图传送不触发 —— 完整排查复盘

> 日期：2026-10-27
> 工程：`My_mmorpg`
> 现象：角色走进传送门，Console 里**一条碰撞日志都没有**，传送不成功。

---

## 一、结论速览

这次一共挖出 **3 个独立缺陷**，任何单独一个都会让传送失效：

| # | 位置 | 问题 | 严重度 |
|---|------|------|--------|
| 1 | `ProjectSettings/DynamicsManager.asset` | **Layer Collision Matrix 里 Default × Default 被关闭**，物理引擎在 broadphase 阶段就把"角色 vs 传送点"这一对丢弃 | 致命 |
| 2 | `Client/Services/MapService.cs:118` | `Request.mapTeleport` 没 `new`，直接赋值 → NullReferenceException | 致命 |
| 3 | `Server/Services/MapService.cs` `OnMapTeleporter` | ① `if` 块缺 `return`；② `MapManager.Instance[source.LinkTo]` 索引键用错（应为 `source.MapID`） | 致命 |

第 1 个是"物理层从来就没工作过"，第 2、3 个是"请求发出去了但半路炸了"。

## 二、排查过程（重点看这一章）

排查的核心手法是：**先判断"卡在哪一步"，再用最少的成本把那一步的事实变成可见的数字**。

传送的完整链路有 5 段，任何一段断了，表现都差不多（"没传送"），必须先把范围缩小：

```
① 物理相交 → ② OnTriggerEnter 回调 → ③ 查表 + 发请求 → ④ 服务器处理 → ⑤ 客户端切场景
```

用户提供的第一个关键信息是「**连碰撞日志都没有**」——这直接把 ④⑤ 排除了，问题锁死在 ①②③。

### 第 1 轮：静态配置全量审查（结果：全部正常）

把能静态验证的全查了一遍，逐项排除：

| 检查项 | 结论 |
|--------|------|
| `DynamicsManager.asset` 的 `m_AutoSimulation` | 1，开启 |
| LayerCollisionMatrix | 首字节 `f8`，**当时误判为"开启"**（后面才发现算错） |
| 传送点 prefab 的 BoxCollider | MainCity 4 个、Map01/02 各 2 个，`m_IsTrigger: 1`、`enabled: 1`、layer 0、`m_IsActive: 1` 全对 |
| 角色 prefab（Warrior1/Archer/Wizard1） | 根节点同时挂了 `Rigidbody` + `CapsuleCollider` + `EntityController` + `PlayerInputController`，layer 0，scale 1 |
| 场景引用完整性 | MainCity 含 TeleporterMainCity 实例，Map01 含 TeleporterMap01，无 Missing |
| 数据文件 | `Client/Data/` 下四个 txt 齐全，无 BOM，JSON 合法，字段与 C# 类匹配 |
| 坐标自洽 | 传送点世界坐标与 `TeleporterDefine.txt` 严格对应（`LogicToWorld: x=X/100, y=Z/100, z=Y/100`） |

**第一轮结论：配置没坏。** 这时候最容易犯的错是"既然都正常，那肯定是别的地方"，然后开始乱猜。

### 第 2 轮：位置对不对（踩了一个 Gizmo 的坑）

推算传送点触发区：门型 4.39 × 4.79 × 1.0，踏板型 4.73 × 0.32 × 4.39，底部齐平在 `y = 8.1`。

用户发了 Scene 截图，看绿色线框是**悬空**的，我一度判定"碰撞体离地悬空，角色够不着"。

**这是一个错误的判断。** 原因在 `TeleporterObject.OnDrawGizmos`：

```csharp
Gizmos.DrawWireMesh(mesh, transform.position + Vector3.up * transform.localPosition.y * .5f,
                    transform.rotation, transform.localScale);
```

它画的是 **mesh 线框**，位置还加了个 `up * localPosition.y * 0.5` 的偏移，**根本不是 BoxCollider 的真实范围**。视觉上"悬空"是假象。

> **教训 1：自定义 Gizmos 只反映代码里画的东西，不能当作碰撞体的真相。**
> 要看真实碰撞体：Scene 视图 Gizmos 下拉只勾 3D Collider，或选中物体看 Unity 自动画的绿框。

### 第 3 轮：用真实坐标算相交（高度假设被推翻）

用户报角色 `y = 8.19`。按胶囊参数（`center.y = 0.968`, `height = 2.08`）算：

```
胶囊世界 y 范围 = 8.19 + 0.968 ± 1.04 = [8.118, 10.198]
门型触发区 y    = [8.10, 12.89]   → 重叠 2.08 m  ✓
踏板触发区 y    = [8.10, 8.416]   → 重叠 0.298 m ✓
```

**垂直方向全部相交，高度不是原因。** 我在报告里保留这个错误过程，因为它是真实排查的一部分——假设错了就明确推翻，不要含糊过去。

### 第 4 轮：把"看不见的状态"变成日志

既然静态全对，就上日志。在三个位置插桩：

1. `TeleporterObject.OnTriggerEnter` 入口 —— 判断回调有没有来
2. `GameObjectManager.InitGameObject` —— 判断角色有没有被判成本地玩家
3. `PlayerInputController.FixedUpdate` —— 加 F9 键直接把角色瞬移到传送点

**这里有个技术细节值得记：瞬移必须改 `rb.position`，不能只改 `transform.position`。**

```csharp
this.rb.position = diagTarget;          // 真正移动物理体
this.transform.position = diagTarget;   // 同步渲染
```

因为 Unity 2017.2 之后 `Physics.autoSyncTransforms` **默认关闭**，只改 Transform 不会立刻同步到物理引擎，物理体还在原地。

日志跑出来的结果：角色输入正常（`判定=本地玩家->输入启用`）、能走（`MoveForward` / `SPD:300`），但**从没有"已进入触发器"**。

同时发现另一个坑：`SetPosition:(5052, 4000, 820)` 换算后是世界 `(50.52, 8.20, 40.00)`，而传送点在 `(6.89, 10.50, 26.00)`，**相距 45.8 米**。

原因是用户报的 `x=6.5, z=25.6` 是**编辑器里把角色拖到门前的位置**，运行时被这句覆盖了：

```csharp
// GameObjectManager.cs:85
go.transform.position = GameObjectTool.LogicToWorld(character.position);  // 服务器下发的存档坐标
```

> **教训 2：编辑器里看到的 Transform ≠ 运行时的实际位置。** 角色位置由服务器数据驱动，必须看运行时的 Console 数值。

### 第 5 轮：决定性的那行日志

F9 瞬移到传送点正中心后，加上 `Bounds.Intersects` 判断：

```
点ID=1 距离=2.70m | 触发区bounds(中心6.9,10.9,26.0 尺寸1.0,4.8,4.4)
                  | 角色bounds(中心6.9,9.2,26.0 尺寸1.0,2.1,1.0) | AABB相交=True
```

**三个轴完全套在一起，`AABB相交=True`，`OnTriggerEnter` 依然不回调。**

到这一步，问题性质变了：**不是"位置没到"，是"几何相交了但物理引擎不认"**。这只能是物理层的过滤规则。

### 第 6 轮：解析碰撞矩阵，锁定根因

`m_LayerCollisionMatrix` 是 32 个 `uint32`（每层一行掩码），YAML 里序列化成 256 个十六进制字符，**小端字节序**：

```python
words = [s[i:i+8] for i in range(0, len(s), 8)]          # 每 8 hex = 1 个 uint32
mask  = int.from_bytes(bytes.fromhex(words[0]), 'little') # layer0 的掩码
```

算出来：

```
layer0 (Default) 掩码 = 0xFFFFFFF8 = 11111111 11111111 11111111 11111000
                                                                    ↑ bit0
bit0 = 0  →  Default 层与 Default 层【不碰撞】
```

完整矩阵（前四层）：

| 行 \ 列 | Default | TransparentFX | IgnoreRaycast | 层3+ |
|---|---|---|---|---|
| **Default** | 不碰 | 不碰 | 不碰 | 碰 |
| **TransparentFX** | 不碰 | 不碰 | 不碰 | 碰 |
| **IgnoreRaycast** | 不碰 | 不碰 | 不碰 | 碰 |
| **层3+** | 碰 | 碰 | 碰 | 碰 |

**角色在 layer 0，传送点也在 layer 0 —— 物理引擎直接把这一对丢掉了。**

> **教训 3：我第一次读这个矩阵时把 `f8` 的 bit0 看成了 1，得出"Default × Default 是开的"的错误结论，导致整整绕了两轮。**
> 十六进制 `0xF8` = `1111 1000`，**最低位是 0**。凡是位运算，务必让机器算，不要用眼睛看。

## 三、修复阶段暴露的连锁缺陷

物理层修好后（掩码 `f8ffffff` → `f9ffffff`），`OnTriggerEnter` 终于进来了，然后立刻炸出下一层问题：

```
NullReferenceException
  Services.MapService.SendMapTeleporter (Int32 teleporterID) (at MapService.cs:118)
  TeleporterObject.OnTriggerEnter (Collider other) (at TeleporterObject.cs:85)
```

### 缺陷 2：protobuf 可空成员没有实例化

```csharp
// ❌ 原代码
message.Request = new NetMessageRequest();
message.Request.mapTeleport.teleporterId = teleporterID;   // mapTeleport 是 null
```

`NetMessageRequest.mapTeleport` 是 protobuf 生成的可空成员，默认 `null`，必须先 new。同一个文件里的 `SendMapEntitySync` 就是对的：

```csharp
message.Request.mapEntitySync = new MapEntitySyncRequest();   // ✓ 它有这一行
message.Request.mapEntitySync.entitySync = new NEntitySync() { ... };
```

修复：

```csharp
// ✓ 修复后
message.Request.mapTeleport = new MapTeleportRequest();
message.Request.mapTeleport.teleporterId = teleporterID;
```

> **教训 4：protobuf 的嵌套 message 一律是引用类型且默认为 null，赋值前必须 new。**
> 这是这套协议代码里最容易漏的一类错误——`netMessage.Request`、`.Response`、各个子 message 都要查。

### 缺陷 3：服务端两处逻辑错误

```csharp
// ❌ 原代码
if (source.LinkTo == 0 || !DataManager.Instance.Teleporters.ContainsKey(source.LinkTo))
{
    Log.WarningFormat("... LinkTo not existed ...");
    // ← 少了 return，接着往下走
}
TeleporterDefine target = DataManager.Instance.Teleporters[source.LinkTo];  // LinkTo=0 时抛异常

MapManager.Instance[source.LinkTo].CharacterLeave(character);   // ← 索引用错
```

**错误 A：`if` 里没有 `return`**，校验形同虚设，紧接着的索引会抛 `KeyNotFoundException`。

**错误 B：`MapManager` 的索引键用错。**

看 `MapManager` 的定义：

```csharp
Dictionary<int, Map> Maps = new Dictionary<int, Map>();

public void Init()
{
    foreach (var mapdefine in DataManager.Instance.Maps.Values)
        this.Maps[mapdefine.ID] = map;      // ← 键是 mapId
}

public Map this[int key] { get { return this.Maps[key]; } }
```

键是 **mapId**（1~4），而 `source.LinkTo` 是**目标传送点 ID**。ID1 的 `LinkTo = 6`，`Maps[6]` 必然抛异常——就算客户端请求成功发出去，服务端也会死在这里。

修复：

```csharp
// ✓ 修复后
if (source.LinkTo == 0 || !DataManager.Instance.Teleporters.ContainsKey(source.LinkTo))
{
    Log.WarningFormat(...);
    return;
}
TeleporterDefine target = DataManager.Instance.Teleporters[source.LinkTo];

MapManager.Instance[source.MapID].CharacterLeave(character);   // 从源地图离开
character.Position = target.Position;
character.Direction = target.Direction;
MapManager.Instance[target.MapID].CharacterEnter(sender, character);  // 进入目标地图
```

> **教训 5："离开源地图、进入目标地图"——两个索引键是两个不同的东西。**
> `LinkTo` 指向"目标传送点"，`MapID` 才是"哪张地图"。混用的后果是查表越界。

## 四、知识点汇总（建议按顺序复习）

### 4.1 Unity 触发器（Trigger）触发的完整条件

`OnTriggerEnter` 被调用的**必要条件**，缺一不可：

1. 双方都有 `Collider`，且**至少一个是 `isTrigger = true`**
2. 至少一方挂 `Rigidbody`（另一方可以是静态碰撞体）
3. 那个 `Rigidbody` 的 `isKinematic` 为 false（静态/kinematic 之间不产生 trigger 回调）
4. 两个 Collider 的 **`enabled = true`**，所在的 GameObject **`activeInHierarchy = true`**
5. **两个 GameObject 所在的 Layer，在 Layer Collision Matrix 里是勾选状态**
6. `Physics.autoSimulation = true`

这次的根因就是第 5 条。

### 4.2 物理引擎的管线，以及层矩阵在哪一步生效

```
Broadphase（粗筛，AABB/空间划分）
  ↓  ← Layer Collision Matrix 在这里就把不配对的组合丢掉
Narrowphase（精算接触点）
  ↓
碰撞回调 OnCollisionEnter / OnTriggerEnter
```

**层碰撞矩阵在最前面就把组合过滤掉了**，所以后面的几何计算、回调统统不会发生。这也是为什么 `Bounds.Intersects` 返回 `True` 却毫无反应——它只是纯数学的 AABB 判断，**完全绕过了物理管线**，不查层，也不查 trigger 标记。

> 这个区别是这次排查最值钱的一条：**"看着重叠"和"物理认为重叠"是两件事。**

### 4.3 `Bounds.Intersects` 能证明什么、不能证明什么

| 能证明 | 不能证明 |
|---|---|
| 两个 Collider 的世界 AABB 在几何上重叠 | 物理引擎会不会处理这对组合 |
| 可以用它快速否定"位置差太远" | 不能替代"是否会触发回调" |

用法：**先用它排除"位置没到"，排除掉之后再往物理配置上查。** 这次就是靠这一步把方向从"位置"切换到"过滤"。

### 4.4 `Physics.autoSyncTransforms` 的坑

Unity 2017.2 起引入，**默认 `false`**。含义：

- 直接改 `transform.position` 不会立即同步到物理引擎
- 物理查询、碰撞检测仍然用旧的内部位置
- 需要手动 `Physics.SyncTransforms()`，或者把该选项打开

这个工程里 `GameObjectManager.cs:85` 用 `go.transform.position = ...` 定位角色，所以**必须把这个选项打开**，否则角色渲染位置变了、物理体还在原地。

另一个更稳的写法：**移动物理体一律用 `rb.position` / `rb.MovePosition`，不要动 `transform`。**

### 4.5 protobuf 可空成员的初始化规则

```csharp
// 错误：直接给子 message 的字段赋值
message.Request.mapTeleport.teleporterId = 1;      // NullReferenceException

// 正确：先实例化
message.Request.mapTeleport = new MapTeleportRequest();
message.Request.mapTeleport.teleporterId = 1;
```

规律：`Request` / `Response` / 各种 `XXXRequest` / `XXXResponse` 全是引用类型，**默认 null**。可以在赋值后统一用 `if (message.Request.xxx == null) message.Request.xxx = new ...` 兜底。

### 4.6 编辑器状态 ≠ 运行时状态

- 在编辑器里拖角色到某位置，运行时会被服务器下发的坐标覆盖（`go.transform.position = LogicToWorld(character.position)`）
- **判断运行时位置只能看 Console 里的逻辑坐标**，公式：

  ```
  world.x = logic.X / 100
  world.y = logic.Z / 100      ← 注意 Y/Z 是交换的
  world.z = logic.Y / 100
  ```

  例如 `SetPosition:(5052, 4000, 820)` → world `(50.52, 8.20, 40.00)`。

### 4.7 "无重力"可能是掩盖物理失效的止痛药

`EntityController.cs:43` 原来是这么写的：

```csharp
// 注释原文：远程玩家保留了 Rigidbody 默认的 useGravity=true，于是在"别的客户端"的视角里，
// 这个被观察的角色会一直受重力下坠（表现为下沉/掉进地面）。
rb.useGravity = false;
```

**这段注释描述的症状，根因就是层碰撞矩阵里 Default × Default 是关的**——角色和地面根本不相撞，开了重力当然一路穿到地心。当时的修法是把重力关掉，把症状压住了，但物理系统整体还是废的。

> **教训 6：当一个"物理现象"需要用关闭物理来修复时，先去查物理配置本身。**
> 症状（掉进地面）和根因（不与地面碰撞）经常看起来风马牛不相及。

## 五、遗留问题（后续处理）

1. **Map02 / Map03 场景里没有传送点实例**
   `TeleporterMap02.prefab` 文件存在（含 ID7/8），但场景里没引用。传送到副本或落日空间后**没有出口**，只能重登。
   处理：把 prefab 拖进这两个场景，跑 `Map Tools → Export Teleporter` 重新导出坐标。

2. **物理第一次真正生效，可能暴露新问题**
   之前角色是"无重力 + 不碰撞"飘着走的，现在会真正和地形、墙体碰撞，而位置又由网络的 `MovePosition` 驱动。可能出现卡墙、抖动、被地面顶起。
   如果发生，方向是：把本地玩家改成 `isKinematic` 或者纯 `MovePosition` 驱动，不要同时让物理引擎和网络逻辑抢位置。

3. **`TeleporterObject.cs:37` 的索引器隐患**
   ```csharp
   TeleporterDefine td = DataManager.Instance.Teleporters[ID];
   if (td == null) { ... }   // 这行永远不会成立
   ```
   字典索引器在 key 不存在时抛 `KeyNotFoundException`，不会返回 null。应该改成 `TryGetValue`，或者像原来一样靠 `ContainsKey` 前置判断。

4. **`OnDrawGizmos` 里的位置偏移**
   `transform.position + Vector3.up * transform.localPosition.y * .5f` 这个写法会让线框和真实碰撞体错位，容易误导调试。建议直接画 `GetComponent<BoxCollider>().bounds`。

## 七、方法论总结（最值得带走的部分）

1. **先分段，再深挖。**
   5 段链路，用一句"连碰撞日志都没有"就砍掉后 3 段。**用户随口的一句现象描述，往往信息量最大。**

2. **每一轮都要有一个可以被证伪的假设。**
   "高度不够"是个假设，拿 `y=8.19` 一算就证伪了。假设被推翻不可怕，可怕的是同时挂着三个模糊猜想，谁也验证不了。

3. **让机器算，别用眼睛看。**
   位运算、坐标换算这类东西，写两行脚本立刻出结果。我第一次用眼睛看 `f8` 就判错了，代价是多绕两轮。

4. **区分"几何真相"和"引擎真相"。**
   `Bounds.Intersects` 是几何，`OnTriggerEnter` 是引擎。两者不一致时，一定存在一层过滤规则，去找那层规则。

5. **症状和根因经常不同域。**
   "掉进地面"的根因是"不与地面碰撞"；"没有碰撞日志"的根因是"物理层从没工作过"。别被症状的领域限定住思路。

6. **别信视觉，信 API。**
   Gizmos 线框悬空是假象，`Collider.bounds` 才是真的。调试时优先用 `Debug.Log` 打印真实数值，而不是看图猜。
